# Day 13 · 从一条「已完成」记录，能推出哪些事实？

[上一天：工具与资源](../day12/README.md) · [Phase 3 阅读索引](../day09/README.md)

用户要的是「核对 A、B 后写摘要」。交接时却发现：计划显示 `completed`，消息历史中也确有两条工具结果，但摘要只列了 A。**这三件事可以同时成立。** 不必先猜模型为何漏写；沿前四天的路径，逐层判断每条记录究竟能证明什么。

## 还原一条可能的执行路径

| 哪一层 | 这一层观察到什么 | 为什么下一层仍可能失败 |
|---|---|---|
| 工具调用 | `c1` 返回 A 的明细，`c2` 返回参数解析错误。两条消息都已回填。 | ID 能配对请求和响应，错误文字却不是 B 的明细。 |
| Agent 循环 | 执行器继续尝试，最后耗尽步数，返回汇总字符串。 | [摘抄 1：达到上限后的返回路径](01_run_result.md)中，停止原因被追加到结果，不是抛给调用者的异常。 |
| 规划器 | `executor.run` 正常返回，[完成标记](../day11/01_plan_step.md)随后写入。 | 调度器没有核对摘要涵盖几笔订单。默认 CLI 则根本没有这一层。 |
| 业务交接 | 读者看到摘要只包含 A。 | 要区分「B 没有订单」和「B 查询失败」，必须回查 `c2` 的内容，不能依据摘要遗漏自行补全。 |

这不是一次实测日志，而是把三个源码分支连起来得到的例子。它给出一条排查顺序：缺少 B 时，先找 B 的调用 ID；有请求无结果，查分发与执行；有结果却是错误，查参数与工具；有正确结果却未进摘要，再查消息保留窗口和最终回答。不同证据会把问题定位到不同层。

## 迁移到自己的应用：保留什么，补上什么？

**保留真实的编排，只替换外部数据来源。** Day 12 的截图测试用假会话替换浏览器服务；[摘抄 2：boss-agent-cli 的样例适配器](02_adapter.md)在另一个项目里展示了相同取舍：提供样例会话时，工厂直接返回 mock 平台。对订单助手，可以让查询接口固定返回「A 有明细，B 缺字段」，仍走真实的消息回填与摘要流程。这样能逐次检查失败是否被如实呈现；它不能代替真实平台的鉴权或网络测试。

**独立定义业务完成条件。** 如果交接要求核对两笔订单，可接受的结果应是「A、B 各自有可追溯的明细」，或者「明确列出无法核对的订单及原因」。不能接受「有两个调用，所以两笔均已核对」。这是订单助手的验收规则，不应伪装成通用 Agent 的退出条件：循环要能在预算耗尽时停下来，即使任务仍未完成。

回看五天，`step` 说明程序又推进了一轮，`tool_call_id` 指向一次具体尝试，`completed` 描述规划器的判断。只有把它们和原始请求、实际结果放在一起，才能回答用户真正关心的问题：**哪笔订单已核对，哪笔还没有，依据是什么？**
