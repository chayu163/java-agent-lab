# Day 12 · 等待超时，报表还会不会写出来？

[上一天：计划状态](../day11/README.md) · [下一天：业务验收](../day13/README.md)

设生成订单摘要要写一份文件。工具五秒没有回传结果，调用者收到了超时。如果直接再发一次写入请求，有可能得到两份文件。要判断能否重试，先分清三件事：**调用者是否还在等，执行者是否还在工作，之前的写入是否已经生效。** 三个问题分别需要证据。

## 相同的「超时」，不同的等待对象

读 [摘抄 1：宿主机等进程，容器终端等输出](01_timeout.md)，关注等待方法接收的是谁，而不是超时是多少秒。

| 路径 | 超时后源码确实做了什么 | 不能从这里推出什么 |
|---|---|---|
| 本机 `PythonExecute` | 父进程等待子进程；若仍存活，请求终止，再限时等待一秒，返回 `success=False`。 | 此分支没有再次检查存活状态；此前写出的文件也不会因返回失败而自动撤销。 |
| 容器终端 | 对 `read_output()` 的等待超时，向调用者报告 `TimeoutError`。 | 没读到最终输出，不等于容器里的命令已终止，更不等于文件不存在。 |

[终端测试](https://github.com/FoundationAgents/OpenManus/blob/99eea8e/tests/sandbox/test_docker_terminal.py#L65-L75)断言调用者看到了超时，并在 `finally` 里关闭终端；它没有断言某个文件未被写入。如果订单系统要求「每次交接只生成一份」，重试前要查的是上一次操作的业务结果，而不只是 Agent 的返回值。这是业务设计要求，不是 OpenManus 已经提供的保证。

## 浏览器返回一张图，又该看哪层证据？

MCP 是应用与工具服务之间的协议。浏览器服务返回图像，还要经过两次转换，才能进入下一轮模型可读取的历史。读 [摘抄 2：对照两个截图测试](02_screenshot.md)：第一个测试用假会话检查服务响应转成的 `ToolResult`；第二个测试用本地图像工具检查 Agent 如何记录结果。前者能发现适配器丢图，后者能发现消息角色或顺序错误。

这里有个看似矛盾的结果：图确实来自工具，却在 `user` 角色的消息里。原因是应用把两项职责拆开：`tool` 消息按调用 ID 配对结果，图像由单独的消息承载。这里的 `user` 是协议角色，不是用户又上传了一次。两个离线测试能证明消息形状正确，不能证明真实浏览器打开过订单页，更不能证明截图里金额正确。
