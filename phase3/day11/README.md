# Day 11 · 「第一步已完成」是谁的第一步？

[上一天：工具调用](../day10/README.md) · [下一天：工具返回](../day12/README.md)

默认 `main.py` 只有 Agent 的步数循环。改从 `run_flow.py` 进入，`PlanningFlow` 才会把任务拆成计划。假设计划只有两项：① 核对订单 A、B；② 写摘要。第一项内部，执行器可能要请求模型、查询两笔订单、再解释结果。**计划步骤是交给执行器的目标；Agent 步骤是执行器朝目标推进的一轮。** 两种「步」不使用同一个计数器。

## 跟一项计划走过内外两个循环

读 [摘抄 1：选中步骤 → 请求执行器 → 标记完成](01_plan_step.md)。外层规划器从计划表选择可执行的一项，把当前计划文本和本项描述组成 `step_prompt`。这是递给执行器的一条请求，不是再创建一个 Agent。`executor.run(step_prompt)` 返回之前，外层在等待；里面运行的正是 Day 9 的循环。完成第一项后，规划器才有机会选择第二项。

| 同一个时刻：订单 A 查到了，B 未查到 | 谁需要这份信息？ |
|---|---|
| 计划表：第 ① 项 `in_progress` | 规划器用下标和状态选择工作；状态里没有 A 的查询结果。 |
| 本步请求：「核对 A、B」 | 执行器据此确定目标；请求本身不能证明已经查到哪一笔。 |
| 执行器历史：`tool(c1, A 的数据)` | 下一次模型请求从历史获得证据；这条消息不自动修改计划状态。 |

再读 [摘抄 2：消息历史保留的是最近几条](02_memory.md)。`Memory` 超过条数上限就保留尾部，没有把旧数据自动压缩进计划。于是计划表仍可显示「已完成」，而当时的订单明细已不在执行器历史中。计划表不是数据库，消息历史也不是审计记录。

## 一个能看清边界的分叉

如果 B 缺少明细，执行器可能**正常返回**「缺少订单 B」，也可能**抛出异常**。两条路径最后都可能呈现错误文字，但调度结果不同：正常返回会走到 `_mark_step_completed()`，这里不检查文字代表成功还是失败；异常则跳过完成标记。由于 `in_progress` 也属于可选状态，后一种情况可能再次选中原步骤，并不保证自动换到下一项。

所以看到 `completed`，准确的读法是「规划器给这项写了完成标记」。要得出「A、B 都核对过」，还需要 Day 10 的两份结果，以及针对订单数据的检查。
