# Day 5 · mini agent loop 知识树

阶段 1 的最后一天。前四天是零件：数据结构（Day 1）、函数与类型（Day 2）、并发（Day 3）、测试（Day 4）。今天把它们装配成一个能跑的 Agent 循环。

```text
agent loop
│
├─ ① 问题：为什么是一次循环而不是一次调用
│   └─ 模型只能输出"下一步做什么"；执行动作、回填结果都在你的程序里
│
├─ ② 协议：messages 的四种角色
│   ├─ system / user / assistant / tool
│   ├─ tool_calls 的字段：id、type、function.name、function.arguments
│   └─ tool 消息靠 tool_call_id 与请求配对
│
├─ ③ 骨架：五个动作
│   ├─ 请求模型         model(messages) -> response
│   ├─ 解析 tool_calls  JSON 字符串 -> 字典
│   ├─ 路由             名字 -> 本地函数
│   ├─ 执行             只读并发，写操作串行
│   └─ 回填与终止       tool 消息入列，判断是否继续
│
├─ ④ 注册表：名字到函数的映射
│   └─ 与 Day 2 的装饰器、Day 4 的替身同源
│
├─ ⑤ 执行策略：并发与串行分开
├─ ⑥ 终止条件：两种正常、三种异常
└─ ⑦ 可观测：每一步留下 trace
```

---

## 一、为什么必须是循环

一次模型调用只能产出一段文本。Agent 之所以叫 Agent，是因为程序在模型之外多做了一件事：**把模型要求的动作真的执行了，再把结果交回给模型**。

```text
用户提问
   │
   ├─> 模型：我需要查订单 A1001        <- assistant, tool_calls
   │      │
   │      └─ 你的程序：查询 -> 结果      <- tool
   │
   ├─> 模型：订单已发货，顺丰 SF123     <- assistant, content
   │      │
   │      └─ 无 tool_calls，结束
   ▼
返回答案
```

模型本身不记得上一轮做过什么，它的"记忆"完全是 `messages` 列表。**循环的每一次迭代，本质上都是重新提交一个更长的列表。**

> [!important] 这一条决定了架构
> 如果模型无状态、记忆全在列表里，那么"Agent 的能力"就等于三件事的乘积：
> 消息列表里有什么（上下文构造）、能调用哪些函数（工具注册表）、循环怎么判断该停（终止条件）。
> 循环本身只有二十行，剩下的复杂度都在这三处。

---

## 二、协议：四种角色

| role | 谁写的 | 关键字段 | 作用 |
|---|---|---|---|
| `system` | 你的程序 | `content` | 定角色、定约束、定工具使用规则 |
| `user` | 用户 | `content` | 本次请求 |
| `assistant` | 模型 | `content` 或 `tool_calls` | 模型的输出：要么给答案，要么要求调工具 |
| `tool` | 你的程序 | `tool_call_id`、`content` | 工具执行结果，回填给模型 |

`tool_calls` 的形状（兼容 OpenAI 协议）：

```json
{
  "id": "call_1",
  "type": "function",
  "function": {
    "name": "query_order",
    "arguments": "{\"order_id\": \"A1001\"}"
  }
}
```

两个容易忽略的细节：

1. **`arguments` 是字符串，不是对象。** 模型生成的是文本，调用方必须自己 `json.loads`。解析失败属于正常情况，要按错误回填而不是让整个请求崩掉。
2. **`tool` 消息必须带 `tool_call_id`。** 模型一次可能返回多个 `tool_calls`，回填时靠这个字段对应。写错或漏写，下一轮模型看到的就是一段没有归属的结果。

## 三、骨架：五个动作

```python
messages = [system_message, user_message]

for step in range(max_steps):
    response = model(messages)
    messages.append(response)

    if not response.get("tool_calls"):
        return response["content"]

    results = execute(response["tool_calls"])
    messages.extend(results)

raise MaxStepsExceeded(...)
```

这段代码只有十几行，但每一行都对应一个可以在面试里展开的设计点：

| 动作 | 要回答的问题 |
|---|---|
| 请求模型 | 上下文怎么构造？历史全带还是截断？ |
| 解析 | `arguments` 解析失败怎么办？缺参数怎么办？ |
| 路由 | 未知工具名怎么处理？谁来决定可调用的范围？ |
| 执行 | 只读与写操作要不要区别对待？并发还是串行？ |
| 回填 | 工具抛异常时回填什么？错误信息给模型看还是吞掉？ |
| 终止 | 步数上限多少？怎么发现死循环？ |

## 四、注册表：名字到函数的映射

模型只能通过**名字**要求调用工具，所以程序必须维护一张表：

```python
TOOLS = {
    "query_order": query_order,
    "get_logistics": get_logistics,
}
```

这张表同时决定两件事：

- 模型能看到哪些工具（发给模型的 `tools` 数组由表生成）
- 名字解析时能落到哪个函数（循环里的路由）

Day 2 写的 `@tool` 装饰器就是自动填充这张表；Day 4 的 `Mock` 则用来在测试里替换表里的条目。两者在这里汇合。

> [!warning] 白名单而非黑名单
> 路由必须是"表里有才执行"。写成 `getattr(module, name)` 会让模型能够调用模块里的任意函数，等于把执行权限交给了模型的输出。

## 五、执行策略：只读并发，写操作串行

模型一次可能返回三个 `tool_calls`。全部串行会浪费等待时间，全部并发则可能撞车。

按副作用分类：

| 类别 | 例子 | 执行方式 | 理由 |
|---|---|---|---|
| 只读 | 查订单、查物流、检索文档 | `asyncio.gather` 并发 | 相互独立，等待时间可以重叠 |
| 写 | 创建工单、退款、发消息 | 依次执行，必要时人工确认 | 顺序影响结果，且通常需要审计 |

Day 3 的 `Semaphore` 与 `gather` 在这一步直接用上。

## 六、终止条件

两种正常结束：

1. 模型返回了 `content` 且没有 `tool_calls`——给出了最终答案。
2. 模型返回 `content`，同时要求调用工具——先执行工具，下一轮再看。

三种异常结束，都必须显式处理：

| 异常 | 触发条件 | 处理 |
|---|---|---|
| 步数超限 | 循环次数到达上限 | 抛出并记录最后一次消息，便于排查 |
| 重复调用 | 连续多轮请求同一组工具且参数相同 | 判定为死循环，中止 |
| 工具持续失败 | 同一工具连续报错 | 中止或降级为"转人工" |

> [!danger] 没有步数上限的循环不是 Agent，是事故
> 模型完全可能反复请求同一个工具。生产环境里这是最常见的失控方式：每一轮都在消耗 token 和工具配额，而调用方看不到任何进展。

---

## 七、可观测：每一步留痕

循环里至少要记录：第几步、模型要调什么、工具返回什么、耗时、是否结束。

这既是调试手段，也是阶段 5 做 eval 的原料——评测时要能回放每一次工具调用，否则无法判断失败出在检索、工具还是模型决策。

## 八、与 Java 的对应

整个循环与 Day 1 的 `Order` 状态机是同构的：

| 本日的循环 | Day 1 的订单 |
|---|---|
| `messages` 列表 | `history` 列表 |
| `tool_calls` | 外部事件 |
| 路由表 `TOOLS` | `_EVENTS` 分发表 |
| 状态转移 | 由模型决定下一步，而非由事件名决定 |
| 终止条件 | 终态 |

区别只有一处：**下一步做什么由模型给出，而不是由代码写死**。所以 LangGraph 那类框架把它建模成图，本质上仍是同一套东西。
